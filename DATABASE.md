# DATABASE.md

Schema source of truth: `prisma/schema.prisma`. Engine: SQLite, single file at
`db/custom.db` (`DATABASE_URL` env). Rationale: a private single-operator tool —
one file to back up, zero infrastructure (the environment stack replaces the
spec's Drizzle/D1 pairing; documented decision in the worklog header).

## Tables

| Model | Purpose | Notable columns |
| ----- | ------- | --------------- |
| `User` | the single operator account | `email @unique`, `passwordHash` (scrypt `salt:hash`), `name` |
| `Company` | org record | `normalizedName` (lowercase/trimmed/punctuation-stripped — dedupe key), website, linkedinUrl, industry, location, companySize, source, status (`Active`/`Archived`), notes, tags (comma-separated) |
| `Campaign` | grouping for outreach | name, description, targetAudience, status (`Draft/Active/Paused/Completed/Archived`), startDate, endDate, notes |
| `Prospect` | the core entity | `linkedinUrl @unique`, `email @unique`, status (14-value lifecycle), priority, fitScore 0–100, researchNotes, outreachAngle, notes, tags; verification block (`verificationStatus`, `verifiedFields` JSON `{name:true,…}`, `verificationNotes`, `verifiedAt`); denormalized lifecycle dates (`dateAdded`, `connectionRequestDate`, `connectionAcceptedDate`, `firstMessageDate`, `lastContactDate`, `nextFollowUpDate`, `followUpCount`, `archivedAt`) |
| `Activity` | audit trail for the whole system | `activityType` (12 values, `src/lib/constants.ts`), `occurredAt`, notes, messageText, **`autoGenerated`** (true = written by automation), FKs to prospect/company/campaign |
| `SavedView` | named filter presets for the prospects table | `entityType` (default `prospect`), `filtersJson` (serialized ProspectsQuery) |
| `Setting` | key/value operator preferences | key `@id`, value (string; `dq_dismissed` holds a JSON array of dismissed DQ issue keys) |

### Status lifecycle on Prospect

14 statuses: Researching → Needs Verification → Verified → Ready → Request
Sent → Connected → Messaged → Follow-Up → Replied → Meeting → Converted
(positive terminal), plus Not Interested / No Response (negative terminals) and
Archived. `lib/constants.ts` groups them into 6 semantic groups; `PIPELINE_ORDER`
drives dashboard/analytics tables. Dates are denormalized from activities by
`lib/automation.ts` — they are read-optimized copies; **Activity remains the
audit trail**. Automation fills dates only when empty and never overwrites.

## Relationships & integrity

- `Prospect.company` / `Prospect.campaign` — optional FK (nullable; set-null on
  company/campaign delete is prevented by guards, see below).
- `Activity.prospect` — **required FK, `onDelete: Cascade`**: deleting a
  prospect deletes its history (the confirm dialog states this explicitly).
  `Activity.company`/`campaign` are optional FKs.
- **Delete guards**: `DELETE /api/companies/[id]` and `/api/campaigns/[id]`
  return **409** when prospects are attached ("move them first"); the UI shows
  the attached count and a link to the filtered prospect list.
- **Duplicate identifiers**: `linkedinUrl` and `email` are DB-level `@unique`;
  creates/PATCHes additionally run app-level checks that return 409 with a
  human message, plus fuzzy guards — company dedupe via `normalizedName`,
  same-name person detection in the DQ scan.
- **Transactions**: every multi-table mutation runs in `db.$transaction` —
  merge (move activities + gap-fill target + delete source), import commit,
  status automation (prospect update + auto activity writes), bulk operations,
  follow-up actions. Partial states are not possible.

## The follow-up design decision (deliberate deviation)

Spec §31 listed a `follow_ups` table. **It was not built.** The queue is derived:
`GET /api/followups` reads every non-terminal, non-archived prospect with
`nextFollowUpDate` and buckets it into overdue/today/tomorrow/week/upcoming,
plus a "no date" section (Connected/Messaged/Follow-Up/Replied without a
scheduled date). `followUpCount` on the prospect records how many follow-ups
were sent.

- **Reason**: spec §16 requires the queue to "update automatically from
  underlying prospect/activity data". A single `nextFollowUpDate` field *is*
  that data; a second table would duplicate dates and invite drift between the
  queue and the record. One source of truth, zero sync logic.
- **Alternative rejected**: `follow_ups` rows (also fails "don't duplicate
  dates"); a cron/materialized queue (no background jobs in this stack).
- Same reasoning applies to the other spec §31 entities that became simpler:
  `tags` are comma-separated strings on Prospect/Company (no join tables), and
  `data_quality_issues` are **computed on demand** by `lib/quality.ts` with only
  dismissals persisted in `Setting` — issues can never go stale.

## Indexes

- `Company`: `normalizedName`, `status`
- `Campaign`: `status`
- `Prospect`: `status`, `companyId`, `campaignId`, `nextFollowUpDate`,
  `dateAdded`, `archivedAt`, `priority` (+ unique indexes on `linkedinUrl`,
  `email`)
- `Activity`: `prospectId`, `companyId`, `campaignId`, `activityType`, `occurredAt`
- `SavedView`: `entityType`

These cover the real query paths: status-group filters, company/campaign drill
downs, the follow-up queue, date-range activity logs, and dedupe lookups.

## Migrations

- Development uses **`prisma db push`** (script `db:push`, with
  `--accept-data-loss`). There is no `prisma/migrations/` directory — the schema
  is single-source and the dataset is small/private. `db:migrate`
  (`prisma migrate dev`) exists in package.json for when tracked migrations are
  wanted; `db:reset` wipes and re-applies.
- Regenerate the client after schema edits: `bun run db:generate`.
- Seed: `bun prisma/seed.ts` (fixtures + login account; not a package.json
  script).

## Backup & restore

The user owns the data; nothing is stored in a proprietary format.

1. **File copy**: stop the dev server, copy `db/custom.db`. That is a complete
   backup. Restore = put the file back (matching `DATABASE_URL`).
2. **JSON backup**: `GET /api/export?type=backup` (also linked in Settings →
   Data & backups) — one file with prospects, companies, campaigns, activities,
   settings, saved views, plus counts and an export timestamp. CSV per entity:
   `type=prospects|companies|campaigns|activities` (prospects honors current
   filters; `&scope=all` exports everything).
3. **Restore path**: the JSON backup is a readable export/audit artifact; full
   DB restore is the file copy. Imports through the wizard are gap-fill only —
   they never overwrite existing values, so re-importing a CSV is safe.
