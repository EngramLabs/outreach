# ARCHITECTURE.md

How Outreach OS is put together. Environment constraint that shapes everything:
**only the `/` route is user-visible** — the app is a single page containing 11
client views; all data access goes through JSON API route handlers.

## Layers

```
┌──────────────────────────── Browser ─────────────────────────────┐
│ src/app/page.tsx  (server component — auth gate)                 │
│   └─ LoginScreen                    …or…                          │
│      Providers (TanStack Query + next-themes) → AppShell          │
│        ├─ Sidebar / Topbar / StatusBar / CommandMenu (⌘K)         │
│        ├─ 11 view components (src/components/views/*)             │
│        └─ global overlays: prospect drawer, import wizard,        │
│           shared dialogs (prospect/company/campaign/activity/     │
│           verify/merge) — driven by the Zustand store             │
│ State:  src/state/app-state.ts (Zustand — view, presets, dialogs) │
│         TanStack Query cache (staleTime 30s, retry 1)             │
│ Client: src/lib/api-client.ts — typed fetch wrapper per endpoint; │
│         401 → window reload → login screen                        │
└──────────────────────────┬────────────────────────────────────────┘
                           │ JSON over HTTP (HttpOnly session cookie)
┌──────────────────────────▼────────────────────────────────────────┐
│ Route handlers — src/app/api/**/route.ts                          │
│   every handler: requireSession() guard → zod validation →        │
│   Prisma queries (+ lib/automation.ts side-effects in the same    │
│   transaction)                                                    │
│ Domain libs: automation.ts, quality.ts, csv.ts, normalize.ts,     │
│              validation.ts, query-utils.ts, constants.ts, types.ts│
└──────────────────────────┬────────────────────────────────────────┘
                           │ Prisma Client (@prisma/client)
┌──────────────────────────▼────────────────────────────────────────┐
│ SQLite — db/custom.db                                             │
│   User · Company · Campaign · Prospect · Activity · SavedView ·   │
│   Setting  (see DATABASE.md)                                      │
└───────────────────────────────────────────────────────────────────┘
```

Server/client boundary: the only server components are `page.tsx` (session gate)
and `layout.tsx` (fonts/metadata). Everything under the shell is `"use client"`
because the whole product is one interactive workbench; all data fetches happen
via `/api`, not server-side render passes (this is the deliberate SPA-style
exception to spec §48, forced by the single-route environment).

## Routing model

- `/` — server component reads the session (`getSessionUser()`): no session →
  `LoginScreen`; valid session → `Providers` + `AppShell`.
- View switching is client-side: `app-shell.tsx` maps `useAppStore().view`
  (one of 11 ids) to a view component. Cross-view navigation passes filter
  presets via `setView(view, preset)` (e.g. DQ "missing company" → prospects
  table pre-filtered; dashboard pipeline row → status filter).
- No server actions anywhere; no `fetch` to anything but `/api/**`.
- `src/app/api/route.ts` is an unused scaffold from the starter (returns
  `{"message":"Hello, world!"}`) — not part of the product; safe to delete.

## Auth flow

1. `POST /api/auth/login` — zod-validated email/password, in-memory rate limit
   (8 attempts/min per email → 429), scrypt verification against the seeded
   `User` row.
2. On success the server sets `os_session`: `base64url({sub,exp}).hmac-sha256`,
   HttpOnly, `SameSite=Lax`, `Path=/`, 14-day expiry (`Secure` in production).
3. Every route handler calls `requireSession(req)` first; invalid/missing token
   or deleted user → 401 JSON.
4. Client side, `api-client.ts` reloads the page on any 401, which re-runs the
   `page.tsx` gate → login screen. `page.tsx` itself is the page-level gate.
   Logout clears the cookie and reloads.

## Automation layer (`src/lib/automation.ts`)

Deterministic rules, all executed inside the caller's Prisma transaction:

- `applyStatusChange` — writes an auditable **Status Change** activity
  (`autoGenerated: true`, note `"old → new"`) for every change; fills lifecycle
  dates **only when empty** (request/accepted/first-message/last-contact);
  sets/clears `archivedAt`; emits the matching contact activity (Connection
  Request / Accepted / Message Sent) only when the date was just filled, so
  re-setting a status never duplicates history.
- `applyActivityEffects` — logging an activity updates dates/status forward
  (e.g. Message Sent → status `Messaged`; Reply Received → `Replied`), never
  moves a prospect out of terminal statuses (Converted / Not Interested /
  No Response / Archived).
- `applyFollowUpAction` — complete / completeAndReschedule / reschedule / skip;
  completion writes a real (non-auto) Follow-Up Sent activity, increments
  `followUpCount`, and either clears or re-sets `nextFollowUpDate`.
- `applyVerification` — merges field-level checkboxes into the `verifiedFields`
  JSON, derives Unverified/Partial/Verified, writes a Verification activity.

Invariants: activities remain the audit trail; denormalized prospect dates are
derived convenience; nothing is ever silently overwritten.

## API surface (all under `/api`; all data routes guarded — only the auth
endpoints login/session/logout are ungated)

| Group | Endpoints |
| ----- | --------- |
| Auth | `login`, `logout`, `session` (POST/POST/GET) |
| Prospects | `/prospects` (GET list w/ filters+sort+pagination, POST), `/prospects/[id]` (GET/PATCH/DELETE), `/prospects/bulk` (status/priority/campaign/archive/restore/delete/verification), `/prospects/merge`, `/prospects/[id]/activities` (POST), `/prospects/[id]/followup`, `/prospects/[id]/verify`, `/prospects/import` (stage=preview\|commit) |
| Companies | `/companies` (GET/POST), `/companies/[id]` (GET/PATCH/DELETE, 409 when prospects attached) |
| Campaigns | `/campaigns` (GET/POST with computed stats), `/campaigns/[id]` (GET/PATCH/DELETE, 409 guard) |
| Activities | `/activities` (GET filtered+paginated, POST), `/activities/[id]` (DELETE) |
| Insight | `/dashboard`, `/analytics` (range param), `/followups` (derived queue), `/research` (stage param), `/data-quality` (GET scan, POST dismiss/restore/reset), `/search` (grouped) |
| Ops | `/settings` (GET/PATCH), `/views` (saved views CRUD), `/export` (CSV per entity / full JSON backup), `/archive` |

Response shapes are typed in `src/lib/types.ts` and mirrored by `api-client.ts`
— the contract between backend and views.

## Deployment

- **Dev**: `bun run dev` on port 3000 (logs to `dev.log`); SQLite at
  `db/custom.db` given by `DATABASE_URL`. In this sandbox external access is
  proxied through an internal gateway — the app itself knows nothing about it.
- **Production path**: standard Next.js Node deployment — `bun run build`
  (standalone output; the script copies `static/` + `public/` into
  `.next/standalone/`), then `bun run start` (`bun .next/standalone/server.js`,
  NODE_ENV=production). Set `AUTH_SECRET` and a durable `DATABASE_URL`; the
  session cookie becomes `Secure` automatically in production.
- **No microservices by design** (spec §47): one process, one database, no
  Redis/queue/container infrastructure. The sandbox Caddyfile/gateway is
  environment plumbing, not part of the app.

## Performance choices

- **Server-side pagination/filtering/sorting** for prospects, activities, and
  archive lists (page/pageSize params; `keepPreviousData` on the client so page
  switches don't flash skeletons).
- **In-memory DQ scan** — `quality.ts` loads prospects/companies and computes
  issues on demand (dismissals persisted separately). Chosen for the
  hundreds-to-few-thousand-records assumption; no background jobs.
- **No chart library** — three small hand-rolled SVG charts (dashboard 14-day
  activity volume; analytics activity-over-time line and prospects-added
  bars); a ResizeObserver supplies the width, tokens supply the colors.
- TanStack Query `staleTime: 30s` + targeted invalidation after mutations
  (`["prospects"]`, `["prospect", id]`, `qk.dashboard`, `qk.followUps`, …) so
  cross-view numbers stay consistent without refetch storms.
- Search inputs debounce (250–350ms) before hitting the API.
