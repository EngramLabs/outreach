# SECURITY.md

Security posture of Outreach OS. Implementation: `src/lib/auth.ts`,
`src/lib/validation.ts`, and the guards in every route handler.

## Auth

- **Single operator.** One account in the `User` table, created by the seed
  (`operator@outreach.local` / `outreach-2024`). Passwords are stored as
  scrypt hashes (`salt:hash`, 16-byte salt, 64-byte key, verified with
  `timingSafeEqual`). There is no registration path, no password reset flow —
  reset means re-seeding or editing the DB directly.
- **Session cookie** `os_session`: payload `base64url({sub,exp})` +
  **HMAC-SHA256** signature (also compared with `timingSafeEqual`); expiry
  14 days (daily-use tool). Cookie attributes: `HttpOnly`, `SameSite=Lax`,
  `Path=/`, `Secure` when `NODE_ENV=production`. Expired or tampered tokens
  fail closed.
- **Login rate limit**: in-memory, per email — more than 8 attempts inside 60
  seconds returns 429. Best-effort for a private app (see Known limits).
- The login screen displays the demo credentials — intentional for this private
  deployment; change the seed before any real use.

## Authorization

- Every data route handler under `src/app/api/**` calls `requireSession(req)`
  before touching the database; a failure returns 401 JSON. The auth endpoints
  are the only ungated ones: `POST /api/auth/login` (the credential check
  itself), `GET /api/auth/session` (returns `authenticated: false` or the
  user's own email/name — nothing else), and `POST /api/auth/logout` (clears
  the cookie).
- Page-level gate: `src/app/page.tsx` is a server component that renders
  `LoginScreen` when `getSessionUser()` returns null — the shell and all views
  never render for unauthenticated visitors.
- Client behavior: `api-client.ts` reloads the page on any 401, which lands on
  the login screen. No route handler trusts the client's session state.
- There are no roles or permissions to misconfigure: exactly one user (spec
  §64 — no multi-tenancy/teams/roles by design).

## Validation

`src/lib/validation.ts` defines zod schemas for **every mutating endpoint**
(prospect create/patch, bulk, activities, follow-up actions, verification,
merge, import, companies, campaigns, settings, saved views, login). Server-side
validation is the source of truth; client forms mirror it for fast feedback but
never replace it. Notable semantics:

- Enums are constrained to the real constant lists (statuses, activity types,
  priorities, campaign/company statuses, verification states).
- `linkedinUrl`/`email` are format-checked on the server; lengths are capped.
- PATCH transforms **preserve `undefined`** (field not sent = leave untouched)
  vs `null`/`""` (clear the field) — a bug where omitted fields were wiped was
  found in QA and fixed (worklog Task 4-a); the transforms now encode this
  contract explicitly.
- Business rules are server-side too: duplicate identifier 409s, delete guards,
  company-by-name dedupe on write, import row cap (2,000).

## CSRF posture

- `SameSite=Lax` session cookie blocks cross-site POSTs from carrying the
  session in the common case.
- All mutations are JSON route handlers: `api-client.ts` sends
  `Content-Type: application/json`, and handlers parse `req.json()` — they do
  not accept form-encoded bodies, so a cross-site `<form>` post cannot mutate
  data. No HTML form ever posts to the API.
- GET handlers are read-only (exports included). No JSONP, no CORS headers are
  opened to other origins.

## Secrets

- `AUTH_SECRET` (env) signs session tokens. **Dev fallback exists**:
  `src/lib/auth.ts` uses a hardcoded `dev-only-secret-change-me…` string when
  the variable is unset. Acceptable only for local development; any real
  deployment must set `AUTH_SECRET` to a random value.
- `DATABASE_URL` points at the SQLite file — no credentials beyond the path.
- Nothing secret is committed: `.env` holds only the DB path; the seeded
  operator password is a documented demo credential, not a secret.
- Exports contain all CRM data (names, emails, LinkedIn URLs, notes) — the
  files must be treated as sensitive and stored accordingly.

## Data safety

- **Destructive actions are confirmed** with affected counts and consequences
  text (`ConfirmDialog`): prospect delete states "the record and all its
  activities are deleted"; company/campaign deletes are refused (409) while
  prospects are attached; bulk actions state the selected count; archive
  restore/delete explain what happens.
- **Imports never overwrite**: commit either creates rows or gap-fills empty
  fields on matched rows — existing values survive every import.
- **Merge is transactional**: activities are moved, the survivor is gap-filled,
  the source deleted — inside one `db.$transaction`, so no half-merged state.
- **Status automation is auditable**: every automated change writes a
  `Status Change` activity marked `autoGenerated`, and lifecycle dates are only
  filled, never silently overwritten.
- Backup paths (file copy + JSON export) are documented in DATABASE.md/README —
  the user is not locked into a proprietary format.

## LinkedIn boundaries (spec §26)

The app **never** automates LinkedIn: no auto connection requests, no auto
messages, no scraping, no browser automation, no bypassing platform
restrictions. It stores URLs and records actions the operator performed
manually. Settings states this scope in plain text. The user remains
responsible for their LinkedIn activity.

## Known limits (honest list)

- **Private app, dev-grade transport**: locally there is no HTTPS termination —
  external access in this sandbox is handled by the environment gateway, which
  is outside the app. The cookie only becomes `Secure` in production builds.
- **No 2FA** — single password factor (deliberate, single operator).
- **Rate limit is in-memory** — it resets on server restart and is per-process;
  sufficient for accidental lockout prevention, not a hardened throttle.
- **Session revocation is coarse**: tokens are stateless (HMAC), so changing
  `AUTH_SECRET` invalidates all sessions; there is no per-session kill switch.
- The seed's demo credentials should be replaced before real data is stored.
